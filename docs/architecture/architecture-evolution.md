# 总体架构方案与演进记录

本文是项目最初的总体方案，也是架构变更的唯一连续记录。每次调整系统边界、核心抽象、关键技术选型或部署模型时，都必须在本文末尾追加带日期的迭代记录；历史结论不删除，只标记其后续状态。

## 0.1 初始方案

### 问题定义

系统需要在上万个 Skill 和多个 Agent 的环境中，以更少 Token、更低延迟和更高准确率完成复杂任务。

### 初始结构

```text
用户请求
  -> 统一编排服务
  -> 意图识别与任务拆解
  -> Skill 元数据检索
  -> Agent 执行
  -> 结果评审
  -> PRD 产物
```

第一版暂定使用单一 Python 服务承载 API、编排、Skill 检索和执行，以最短路径验证业务闭环。外部存储与模型通过适配器访问，避免核心逻辑绑定供应商。

### 初始原则

- 只常驻轻量 Skill 元数据，完整指令按需加载。
- Agent、Skill 与 Tool 是不同资源，不在模型层混为一体。
- 先形成可运行闭环，再拆分分布式服务。
- 每次执行必须记录路由、Token、延迟和评审结果。

## 迭代记录

### 2026-05-02 · v0.1 · 建立单体参考架构

- 修改内容：建立单一 Python 编排服务、Skill 元数据目录和 PRD 生成参考场景的初始边界。
- 修改原因：项目尚处于问题验证期，先减少基础设施变量，验证能力检索是否能降低上下文开销。
- 影响范围：仅形成文档与工程约束，尚未冻结运行时、存储和协议实现。
- 后续验证：以 100、1,000、10,000 个 Skill 的路由实验比较 Token、召回率和延迟。

### 2026-05-05 · v0.2 · 项目更名为 NexusOS（纽带）

- 修改内容：将工作名称 AgentOS-Lab 更改为 NexusOS，中文名确定为“纽带”，并确立独立文档域名 `nexusos.net.cn`。
- 修改原因：旧名称容易被理解为教学实验；新名称更准确地表达连接 Agent、Skill、Tool、Memory、Knowledge 与人的基础设施定位。
- 影响范围：项目标识、文档站配置、公开描述和后续模块命名统一使用 Nexus 前缀。
- 兼容说明：本次仅改变品牌与表述，不改变 v0.1 的验证边界。

### 2026-05-09 · v0.3 · 采用 Contract First 与六边形内核

- 修改内容：把“单一 Python 服务”细化为模块化单体；领域层只依赖 Agent Runtime、Skill Repository、Model Gateway、Memory Store 等端口，供应商 SDK 位于适配器层。
- 修改原因：如果业务逻辑直接依赖 LangGraph、模型厂商或向量数据库，后续无法做运行时对照实验，也难以演进到多语言服务。
- 影响范围：后续代码必须从稳定契约开始，默认实现可以留在进程内，但不能让基础设施类型泄漏到领域模型。
- 取舍：模块化单体增加少量接口代码，换取可测试性、替换能力和后续服务拆分路径。

### 2026-05-14 · v0.4 · 冻结第一组领域契约

- 修改内容：将 Goal、Task、TaskGraph、NexusState、AgentRuntime、SkillRepository、MemoryStore、ToolGateway 和 RunRepository 落为框架无关的 Python 契约。
- 修改原因：在引入工作流框架与存储前先验证依赖方向，避免实现类型泄漏到领域模型。
- 影响范围：任务图必须是有向无环图；所有运行时统一返回 AgentResult；运行状态可由任意适配器持久化。
- 兼容策略：契约仍处于 `0.x`，允许通过新增可选字段演进，破坏性变更必须补充 ADR。

### 2026-05-24 · v0.5 · 固化 Skill 渐进加载边界

- 修改内容：把 Skill 拆分为常驻索引的 `SkillSummary` 与命中后读取的 `SkillPackage`，统一使用版本化 Manifest 描述领域、能力、关键词、工具依赖、成本、风险和历史质量。
- 修改原因：完整 Skill 指令和示例随目录规模线性进入上下文会造成 Token 爆炸，检索阶段只需要少量可排序元数据。
- 影响范围：Registry 扫描时禁止读取指令正文；Executor 只能在 Router 完成策略过滤和选择后加载完整包。
- 取舍：Manifest 维护成本增加，但获得了可索引、可验证、可版本化和可审计的能力目录。

### 2026-06-03 · v0.6 · 从单一相似度升级为多信号路由

- 修改内容：将初始“Skill 元数据检索”细化为领域识别、语义与词法相关度、能力匹配、历史成功率、成本和延迟的加权排序，并在选择前执行工具、风险与领域硬约束。
- 修改原因：单一向量相似度不能表达授权、成本和可靠性，容易选出语义相关但不可执行或性价比过低的 Skill。
- 影响范围：每个候选必须携带可解释评分分量；Token 预算成为 Router 的输入；生产向量检索仅替换召回信号，不绕过策略层。
- 当前限制：离线实现使用确定性词法近似，后续通过 Qdrant 适配器引入真正的稠密与稀疏混合召回。

### 2026-06-12 · v0.7 · 增加显式上下文预算

- 修改内容：在 Runtime 前增加 Context Budget Manager，将系统、任务、Skill、Memory、检索证据、工具 Schema 和输出预留分别设定预算。
- 修改原因：路由只解决“选哪些能力”，不能阻止历史消息、检索结果和工具描述继续挤占上下文。
- 影响范围：Agent Runtime 只能接收已经构建的 `AgentContext`；必要上下文不能静默截断；所有省略项与分区用量进入预算报告。
- 取舍：离线 Token 估算只保证保守和确定性，生产环境由模型适配器提供准确 tokenizer。

### 2026-06-14 · v0.8 · 将 Memory 按生命周期分层

- 修改内容：Memory 明确拆分为 Working、Episodic 与 Semantic 三类，并通过统一 `MemoryStore` 端口向 Context Builder 提供候选片段。
- 修改原因：当前任务状态、历史运行经验和长期知识具有不同的一致性、查询与保留要求，使用单一聊天记录无法可靠治理。
- 影响范围：本地开发使用支持中英文检索的内存适配器；生产规划分别映射到 Redis、PostgreSQL 和 Qdrant，但领域层不感知产品类型。
- 隐私约束：跨运行检索后续必须增加租户、用户和数据分类过滤，不能把全局相似度作为授权依据。

### 2026-06-20 · v0.9 · Agent 从固定角色改为声明式发现

- 修改内容：新增版本化 Agent Registry 与基于任务能力、领域的 Agent Resolver；工作流不再直接写死角色实现。
- 修改原因：固定 `PM -> UX -> Tech -> Writer` 链条无法根据任务复杂度增减专家，也会把角色、Skill 和 Tool 权限混在一起。
- 影响范围：Planner 只声明任务所需能力；Resolver 选择 Agent；随后 Router 必须在 Agent 的 Skill 与 Tool 策略内选能力。
- 安全收益：Agent 的工具白名单由 Manifest 声明，后续 Policy 层可以在执行前进行独立复核。

### 2026-06-21 · v0.10 · PRD 流程从固定顺序改为能力导向 DAG

- 修改内容：Planner 生成只声明依赖与所需能力的任务 DAG；标准需求并行执行 UX 与技术评估，复杂需求额外并行行业研究。
- 修改原因：固定 Agent 链既浪费并行机会，又把规划结果与当前角色目录绑定，无法验证动态组队。
- 影响范围：Agent Resolver 成为 Planner 与 Runtime 之间的必经步骤；运行时按拓扑层调度；工作流必须先通过 DAG 不变量校验。
- 应用边界：PRD 任务模板位于 Reference Application，通用核心只保留 Goal、Task 与 TaskGraph。

### 2026-06-21 · v0.11 · 建立可离线验证的进程内 Runtime

- 修改内容：把 Planner、Agent Resolver、Skill Router、Context Builder、Memory 与 `AgentRuntime` 端口串成完整执行闭环，并按 DAG 拓扑层并发执行。
- 修改原因：只有可重复的端到端运行才能暴露模块边界问题；早期直接依赖在线模型会让测试受网络、费用和模型漂移影响。
- 影响范围：新增确定性 Local Runtime 作为测试适配器；任务级记录 Agent、Skill、预算、Token、产物和生命周期事件；失败任务停止当前运行。
- 后续替换：Local Runtime 不作为生产推理方案，下一阶段在同一端口后接 LangGraph 和模型网关。

### 2026-07-04 · v0.12 · 固定传输层与应用服务边界

- 修改内容：增加 FastAPI 工厂与 `/v1/prd/runs` v1 传输契约，使用独立 Bootstrap 组合应用依赖；API 只做参数校验和序列化。
- 修改原因：如果 HTTP 类型进入编排器，CLI、Worker 和测试将无法复用同一应用服务，也会让未来从同步请求迁移到异步运行变得困难。
- 影响范围：核心包不强制依赖 FastAPI；所有入口通过 Composition Root 构建端口实现；v1 响应保留任务选择、评审、Token 和产物。
- 演进路径：当前接口同步返回完成结果，分布式 Runtime 上线后增加状态查询，同时保持已公开字段的兼容性。

### 2026-07-11 · v0.13 · 模型调用收敛到统一 Gateway

- 修改内容：新增与供应商无关的消息、请求、响应与 Token 用量契约，并提供离线确定性实现和 OpenAI-compatible HTTP 适配器。
- 修改原因：Agent 直接持有供应商 SDK 会让模型切换、成本统计、降级和数据策略分散在各个节点，无法统一治理。
- 影响范围：Runtime 只依赖 `ModelGateway.complete`；供应商模型名、鉴权和响应格式由适配器处理；Token 用量必须映射到核心模型。
- 后续能力：模型选择、fallback、限流和内容策略将在 Gateway 上层独立演进。

### 2026-07-12 · v0.14 · 明确 LangGraph 与 Temporal 的分层职责

- 修改内容：`AgentRuntime` 增加可选 LangGraph 实现；LangGraph 管理单个 Agent 的推理图，Temporal 被限定为未来跨服务、长时间业务流程的外层编排。
- 修改原因：两套框架都提供恢复与重试，如果不先划定状态和失败所有权，会出现重复执行、双重 Checkpoint 与不可预测的重试叠加。
- 影响范围：LangGraph 状态必须在适配器内转换；Temporal Activity 未来只调用 Nexus Task 边界；同一业务状态只能有一个主数据源。
- 实施顺序：当前启用 Local 与 LangGraph Runtime，Temporal 在远程 Worker 契约和幂等语义完成后接入。
