# NexusOS · Nexus PRD 产品需求文档

> **纽带系统核心思想：AI 理解用户需求，按需组装完成任务所需的能力与界面组件。PRD 页面只呈现编写 PRD 所需的组件，同一功能保留一个主要入口；其他组件在需要时出现，不重复铺设、不硬占位。** 此原则适用于后续全部任务，详见[架构总览](../../architecture/overview.md)。

**界面形态保持软件式工作台：菜单栏、工具栏、左侧管理、中间编辑、右侧 AI、底部状态栏。优化重点是信息分组、去重和按需展开，不是取消外壳或改成普通表单页。**

版本：0.2 草稿 · 日期：2026-09-10 · 状态：待产品负责人评审

本稿根据项目原始讨论、当前代码和本次产品方向整理，由开发协作直接编写，供 Nexus PRD 导入、评审和继续修订。它不是本产品已通过真实模型验收的证明。

## 1. 背景与问题

NexusOS（纽带）的长期目标是连接 Agent、Skill、模型、工具、知识与人工决策，验证复杂任务中的能力选择、多 Agent 协作和 Token 效率。项目同时服务于学习、开源与工程能力展示。[S1]

当前产品优先级已经收敛：先让 Nexus PRD 能写真实的软件产品需求，其他业务应用随后扩展。[S2]

原实现的 PRD 页面通过固定延时展示记账产品内容，与输入的产品主题无关；页面上的保存状态和完整度没有持久化与评审结果支撑。Python 默认参考 Runtime 也输出固定模板。它们可以验证工程链路，却无法支撑日常写作。[S3]

需要解决的核心问题是：用户已经给了背景、约束和材料，系统仍可能生成通用提纲、遗漏规则、把假设当事实；用户缺少可控的编辑、追问、修订与交付过程。

## 2. 产品目标与非目标

### 2.1 本期目标

让用户完成一个可持续工作的闭环：输入需求和证据 → 补充关键问题 → 生成具有业务规则和验收条件的初稿 → 人工编辑或按反馈修订 → 保存版本 → 导出用于团队评审。

“可用”的最低含义包括：内容与具体产品有关；已确认的范围不丢失；未知内容显式标注；有可观察的验收结果；刷新或重启后可继续；失败不会抹掉已保存成果。

### 2.2 非目标

本期不推出独立竞品研究、技术方案生成或技能商城应用；不实现多人实时编辑、公网多租户、企业单点登录、自动抓取网页、PDF/DOCX 解析、自动发布到外部系统。以上为后续扩展，不在界面中展示为可用能力。

NexusOS 继续保留通用编排、Skill 路由与多语言边界。本期不以部署更多微服务作为 PRD 可用性的验收条件。[S1][S2]

### 2.3 成功指标

| 指标 | 口径与采集方式 | 首版验收依据 |
| --- | --- | --- |
| 写作闭环完成 | 一份需求完成输入、生成、编辑、保存、重开、修订、导出 | NexusOS 自身与另一个不同主题的软件产品分别实测；两者均完成 |
| 已确认要求覆盖 | 人工逐项对照简报中的必做、禁做和约束，在正文或待确认清单中找到对应位置 | 核心范围无遗漏，无未标注的扩大范围 |
| 可验收性 | 逐条检查首版功能是否有角色、规则、异常与可观察的验收条件 | 核心功能不能仅描述“支持”“智能”“高效” |
| 保存可靠性 | 保存后刷新、重启服务、从文档库重开并对比正文 | 已保存内容一致；冲突不得静默覆盖 |
| 事实诚实性 | 检查引用编号和材料、未经验证的外部事实、假设标签 | 无伪造来源、虚假联网研究或虚假评审通过 |
| 运行成本 | 记录每次模型返回的输入/输出 Token，并关联实际阶段 | 先建立真实样本基线；成本与时延目标数值待确认 |

以上是验收要求，不是已经达成的线上统计。

## 3. 用户、角色与场景

首版目标使用者是项目维护者与需要编写软件需求的产品经理；读者是研发、设计和测试。单用户在当前机器或个人虚拟机使用属于暂定部署假设，需产品负责人确认。

典型场景：

- 有想法而没有规格：描述目标和用户，通过提示补充范围、限制和验收期待，生成初稿。
- 已有访谈和讨论：导入 Markdown/TXT 或粘贴材料，要求文档指出结论来源。
- 已有 PRD：导入正文、补充本次修改要求，生成新版本，保留旧稿。
- 收到评审意见：指出要修改的 FR 编号和约束，修订后再次核对验收条件。
- 为 NexusOS 自己写需求：使用预填简报或导入本稿，逐步确定下一期产品范围。

| 优先级 | 内容 | 交付边界 |

| P0 | 模型生成与独立评审 | 对应具体产品，明确假设；无模型时明确不可生成 |
| P0 | 正文编辑、预览、持久化、版本 | 人工编辑是可保留的正式输入 |

| P0 | 任务状态、失败、停止、重启恢复 | 不展示虚构进度，不自动重放付费任务 |

## 5. 信息架构与用户流程

工作台 → PRD 工作区。工作区包含“需求与材料”“PRD 正文”“版本历史”；侧栏提供缺失信息、反馈修订、评审意见、实际任务记录和文档库。

新建主流程：填写简报 → 保存 → 发起生成 → 查看真实阶段 → 阅读初稿和评审问题 → 修改 → 保存或 AI 修订 → 导出。

资料不足：仍允许先生成，明确保留待确认问题。材料只提供链接时不假装读取，提示提供正文。

生成失败：展示失败状态与可采取的下一步。若正文已生成而评审失败，允许继续编辑或仅重试评审。

编辑冲突：显示冲突提示，保留本地草稿；用户重新打开服务器版本并选择如何合并，不进行无提示覆盖。

## 6. 功能需求

### FR-001 创建和维护需求简报（P0）

角色：作者。入口：工作台自然语言输入或 PRD 新建。

输入字段：产品名称、产品构想/场景、目标用户、问题/依据、首版范围/非目标、约束、成功指标、可选模板。产品名称必填；其余允许暂缺。工作台输入必须传入简报，不能丢失。

规则：产品名称去除首尾空白后为 1–200 字符。正文和材料分开存储。用户明确的必做与禁做优先于模型建议。简报编辑后，旧评审不得作为当前版本的有效评审。

异常：未填名称阻止保存和生成；字段过长显示具体错误。尚无服务器文档时显示“新文档”，不得显示已保存。

验收 AC-001：给定工作台输入“护士排班”，进入 PRD 后场景字段含该输入；保存并重开后全部字段一致。

### FR-002 收集参考材料（P0）

角色：作者。前置：已进入需求编辑区。

主流程：导入 .md/.txt 文件或添加来源名称与正文 → 显示编号 S1、S2 → 保存 → 在生成和评审上下文中携带完整来源内容。

规则：最多 12 份材料；名称必填且不超过 200 字符；每份正文 1–20,000 字符，合计不超过 50,000。删除后编号随当前材料顺序更新，同时旧评审失效。版本保存其当时的简报与材料，避免历史引用被新材料替代。

异常：拒绝不支持格式和过大材料；不静默截取正文。URL 按文本处理，不等于已经抓取。远程图片不自动加载。

验收 AC-002：给定两份材料，生成阶段收到 S1、S2 及其正文；正文引用可以回到同版本材料；非法格式不会被当作已成功导入。

### FR-003 提示关键信息缺口（P0）

角色：作者。触发：某个核心简报字段为空。

行为：按场景、用户、问题、范围、约束和成功指标提示缺口；点击问题定位相应字段。填写后该缺口从提示中移除。

规则：这些提示描述填写状态，不能冒充基于用户访谈得到的判断。允许跳过后生成，但模型须把未知信息列为待确认，不得擅自填入目标数值或业务承诺。

验收 AC-003：未填范围时显示范围问题，填写后消失；未填目标值时，生成初稿不能凭空承诺一个已确认目标。

### FR-004 生成完整 PRD（P0）

角色：作者。前置：名称有效、简报已保存、模型已配置、没有活动任务。

阶段：需求与范围 → 用户流程与异常 → 数据与可行性 → 完整写作 → 独立评审。每阶段根据能力选择 Agent，按需加载相关 Skill。各阶段保留原始简报和来源，不依赖被多次摘要的材料来恢复用户约束。

正文至少覆盖：问题证据、目标与非目标、用户场景、首版范围、流程、逐项功能和业务规则、页面与交互、数据与权限、非功能约束、验收与发布、风险和待确认事项。提供模板时优先遵守模板，同时指出缺少的关键内容。

每项核心功能需要稳定的 FR 编号和对应 AC；用户未确认的功能标为建议。不得输出另一产品的固定功能，不得声称联网查询过。

异常：模型未配置时阻止生成；调用失败或内容为空时明确失败。响应被截断时自动续写，达到续写次数后仍不完整才失败，不使用离线模板冒充结果。模型服务拒绝过长输入时要求精简材料，不悄悄丢弃用户输入。

验收 AC-004：分别输入 NexusOS PRD 工具与排班工具，输出应体现各自角色、范围和规则；禁止事项没有变成默认功能；截断输出不能覆盖已保存正文。

### FR-005 编辑、预览与保存（P0）

角色：作者。入口：PRD 正文。

行为：切换 Markdown 编辑和预览；支持标题、列表、表格、引用和代码块。编辑正文后显示未保存状态。浏览器草稿提供恢复辅助，服务器保存才显示“已保存”。

规则：保存请求包含预期修订号；服务器事务内校验，内容冲突返回错误。保存成功增加修订；内容未变的重复保存不产生无意义版本。生成或评审期间暂不允许编辑同一份文档。

异常：网络中断、浏览器存储不足和跨页编辑都不能显示保存成功。重新打开时发现浏览器草稿，允许恢复或采用服务器版本。正文中的 HTML 不执行脚本。

验收 AC-005：人工修改后保存、刷新、重启再打开内容一致；两个页面持有旧修订时，后保存者收到冲突且服务器内容未被覆盖。

### FR-006 结构化质量评审（P0）

角色：作者、评审读者。输入：当前完整正文、当前简报、来源。

输出：结论摘要与问题清单；每项含严重程度、具体章节/FR、问题依据、可执行建议。严重程度分阻断、主要、建议。

检查：范围遗漏与扩大、业务规则、角色权限、失败与恢复、FR/AC 对应、指标口径、来源与假设、章节之间的一致性。

规则：不生成固定完整度分数；没有发现问题时显示等待人工评审，不能自动宣称需求已批准。编辑正文或简报后评审失效。模型返回非法评审结构时记录失败，已写出的正文保留。

验收 AC-006：给定缺少异常规则的需求，评审意见能指出具体位置并提出修改；非法 JSON 不能被显示为通过，正文仍可重新打开。

### FR-007 根据反馈修订（P0）

角色：作者。前置：已有正文，无活动任务，修改要求非空。

主流程：输入反馈 → 保存当前人工编辑 → 将当前全文、简报、来源、修改要求和上次评审交给写作阶段 → 生成完整新稿 → 独立评审。

规则：保留已有 FR 编号和未要求修改的内容；不以最早版本替代当前人工修改。新稿保存为新版本。模型对“仅修改指定范围”的遵循仍须通过差异人工检查；自动差异视图列为后续能力。

验收 AC-007：先人工补充夜班时长，再要求修订冲突规则；修订输入含人工约束，输出保留该约束和旧 FR 编号，旧版本可找回。

### FR-008 版本历史与恢复（P0）

角色：作者。行为：查看版本序号、时间、来源说明，预览历史正文；选择历史版本载入编辑区。

规则：历史快照同时包含正文与简报。恢复需要再次保存才成为当前正式版本；旧版本不删除。单独评审不新增正文版本。

验收 AC-008：v1 生成、v2 人工修改后，载入 v1 并保存，形成 v3；v1、v2 内容保持不变。

### FR-009 导出交付文档（P0）

角色：作者。行为：导出当前编辑内容为 Markdown 或独立 HTML；文件名来自产品名称并移除文件名非法字符。

规则：导出取当前编辑区正文，包含未保存修改；此操作不能冒充服务器保存。HTML 支持中文和表格，可离线阅读，不加载外部脚本或图片。HTML 是展示格式，Markdown 仍为可编辑源。

验收 AC-009：修改一段未保存正文后导出，两种文件均含该段；离线打开 HTML 表格可阅读，正文内的脚本不执行。

### FR-010 任务状态与恢复（P0）

角色：作者。状态：排队、执行中、成功、失败、已停止。界面展示实际阶段，禁止模拟百分比或虚构置信度。

规则：一个文档同时最多一个活动任务；服务级同时最多两个执行任务，其余排队。发起任务后无需保持页面打开。停止任务阻止后续阶段和迟到结果覆盖文档；已经发出的模型请求可能仍由供应商完成和计费，停止不保证撤销供应商计算。

保存每个成功阶段的输出、Agent、Skill 与模型返回用量，供排错。模型缺失用量时不推算为真实用量。当前用量仅统计收到并通过 Runtime 校验的响应，供应商失败/截断响应的计费须以供应商账单为准。

服务重启后将未完成任务标成中断，不自动重新调用付费模型。已保存正文可继续使用；评审失败时支持只重试评审。

验收 AC-010：执行中关闭页面再打开可继续看状态；停止后旧任务不再修改正文；重启后中断任务解除编辑锁且不会自动产生额外模型调用。

## 7. 数据与状态

| 对象 | 关键字段 | 约束 |
| --- | --- | --- |
| 文档 | id、brief、content、revision、version、review、active_job_id、last_job_id、时间 | ID 由服务器生成；revision 用于并发校验；正文最多 200,000 字符 |
| 简报 | 产品名、场景、用户、问题、范围、约束、指标、模板、sources | 已确认输入保留原意；来源随版本快照保存 |
| 版本 | document_id、version、brief、content、note、created_at | 仅追加，不能覆盖旧版本 |
| 任务 | action、instruction、status、stage、steps、error、Token、时间 | action 为生成、修订或评审；终态不可被迟到响应改回执行中 |
| 评审 | summary、issues、status、notice | AI 意见；人工验收结论不由模型自动写入 |

首版采用本机 SQLite 持久化，限定一个 API 实例。数据库和浏览器草稿含用户原文，应由使用者控制运行环境。数据删除、保留期限、团队授权与备份周期尚未形成确认需求；不得将个人工作区直接描述成有租户隔离的公共服务。

## 8. 非功能与实现边界

可靠性：保存、版本创建、任务占用在事务内执行。模型故障不会触发离线假结果；不可用依赖有明确提示。

安全：模型密钥只在 API 服务环境中配置，不进入浏览器或任务结果。Markdown 展示不执行原始 HTML，不自动加载远程图片。PRD 工作区尚未实现用户认证，首版限定个人机器或受保护环境。

性能：API 创建任务返回任务标识，长时间模型调用不占用浏览器请求。延迟与质量目标待真实模型基线确认；长正文统一分段生成，单段截断时自动续写，不依赖人工配置全局上下文或输出上限。Token 估算仅用于追溯展示，不作为拒绝请求的依据；模型服务仍对自身上下文窗口负责。

架构：Python 承担智能编排，LangGraph 承担单 Agent 执行图，TypeScript 构建 Studio；现有 Go Runtime、Go MCP Gateway、Rust Router 保留未来扩展边界。本期不把 SQLite 工作区标成已完成企业存储集成。

## 9. 发布验收矩阵

| 场景 | 关联需求 | 验证方法 |
| --- | --- | --- |
| NexusOS 自身完整 PRD | FR-001–FR-010 | 导入本稿或预填简报，真实模型生成/修订并由维护者逐项评审 |
| 另一主题软件 PRD | FR-002、FR-004、FR-006 | 自带简报和证据，检查领域规则、禁做事项、来源与验收 |

## Studio 交互增补 · 2026-09-11

编写路径新增“原型设计与确认”：配图按原型图管理，用户可导入现有图片、手动组织页面或由 AI 生成可点击线框，再确认页面和交互说明。确认后的截图及说明随 PRD 发布和导出，改动简报后需重新确认原型。AI 对话根据当前编辑对象服务于澄清、原型修改或正文修订，避免重复标签与模式按钮。

任务启动后打开独立运行区域，Flow 显示真实进度，运行节点呼吸高亮，点击可查输出和执行能力；同一区域内提供中文运行记录与历史追溯。菜单和底部状态栏保留，不增加单独的运行按钮行。新组件须遵守本文显著标注的纽带系统核心思想，详见工作台设计文档。
