# RT-003：PRD 失败现场与检查点恢复

状态：已实现单实例、用户显式触发的阶段恢复；自动恢复调度、跨实例租约与工具副作用幂等仍待实现。日期：2026-09-10。

## 发现过程

用户反馈生成失败后只有重新发起任务，不能利用已经完成的分析。查询本机 `prd_jobs` 和只追加追溯事件，确认以下事实（时间为北京时间）：

| 任务 | 时间 | 已完成阶段 | 失败证据 |
| --- | --- | --- | --- |
| `5a07217ae1bb4fd3b887aee99a3bc80c` | 2026-09-10 15:35:41 提交 | requirements、ux、technical | write 返回 finish_reason=length，output_tokens=8000 |
| `66f2112c64684dca81584b16ab8ecfc4` | 2026-09-10 15:52:43 提交 | 无 | requirements 返回 finish_reason=length，output_tokens=4001 |

因此不能把所有失败都解释为“最后一步失败”，也不能把完整原始响应的存在当作阶段已完成。第一次任务已有三步可复用，第二次没有成功阶段，继续执行仍需重新请求需求分析。

根因有两层：供应商响应达到输出上限；系统仅保存追溯和阶段展示数据，没有恢复执行契约。检查点解决已完成工作重复执行的问题，不保证原先的截断、认证或格式错误自行消失。排查操作见 [Trouble Shooting](../trouble-shooting.md)。

## 技术选择与嵌入

使用 LangChain 生态中 **LangGraph 的 `AsyncSqliteSaver`**，依赖 `langgraph-checkpoint-sqlite`，并保留事务内业务阶段检查点。LangGraph 原生持久化按 thread 保存节点状态，SQLite 适用于当前单实例边界。[官方持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)

| 层 | 实现与职责 |
| --- | --- |
| `PrdWorkflow._run` | 每次执行打开异步 SQLite saver，退出时关闭；检查点文件为业务数据库路径加 `.checkpoints` |
| `LangGraphRuntime.execute` | `compile(checkpointer=...)`，thread_id=`job_id:stage_id`；节点保存归一化响应字典。完整性与评审 JSON 校验通过后才返回节点结果 |
| `PrdStore.complete_stage` | 在同一事务写阶段内容、SHA-256 证据对象、用量、步骤状态、`stage.succeeded` 和 `checkpoint.saved` |
| `PrdStore.start_job` | 验证恢复来源、文档修订和互斥，固定原始输入，拷贝已完成阶段与来源关系，创建独立执行任务 |
| `PrdStore.publish` | 正文/评审保存和发布标记同事务；恢复到已发布位置时不重复创建版本 |
| Studio | 主编辑区顶部任务状态条和“全程追溯”均提供“重新执行”“继续执行”，显示已完成阶段数量与不可继续原因 |

本实现的跨阶段执行计划仍由 `PrdWorkflow` 管理，并非把整条 PRD 流程转换成一个 LangGraph，也不是恢复 Python 调用栈。每个任务使用独立 thread，避免修改原任务的失败证据；继续执行优先读取业务检查点，再在“模型节点已提交、业务阶段尚未提交”的窗口读取来源 thread 的完整终态。新调用进入新任务 thread，旧 thread 保留。

## 两种操作的契约

| 操作 | 输入 | 已完成阶段 | 产物与关联 |
| --- | --- | --- | --- |
| 重新执行 | 当前保存的需求和文档；沿用所选任务的动作与修订指令 | 全部重跑 | 保留旧版本，新建任务与 `retry_of_job_id`；生成/修订成功追加版本 |
| 继续执行 | 原任务输入快照 | 复用已确认成功阶段，仅重跑缺少成功检查点的阶段 | 新建任务与 `resume_of_job_id`；沿用已发布正文，不重复写版本 |

沿用现有 `POST /v1/prd/documents/{id}/jobs`，新增 `resume_of_job_id`，与 `retry_of_job_id` 互斥。继续执行的 action/instruction 由服务端从来源任务确定。仅同文档的失败/已停止任务可作为来源。

继续执行要求：文档修订号仍等于原任务最后一次业务发布的修订号，来源是该文档最近任务，且文档没有活动任务。浏览器有未保存改动时按钮禁用；服务器独立校验已保存变更并返回 409。`recovery.can_resume/reason/completed_stages` 随任务查询及历史返回，旧页面不能绕过互斥。

正文统一采用三个写作片段，检查点契约版本为 `prd-stages/v1`，不兼容时拒绝继续，要求重新执行。连续失败时继承可复用阶段和 Runtime 来源列表。分段合并校验失败会失效三个写作片段，保留已完成分析，避免每次继续都再次合并同一份不合格内容。

## 旧任务兼容与追溯

旧任务必须有原始输入快照；没有快照时禁止推测现场。仅从 `stage.succeeded` 事件中导入允许的分析/写作阶段，记录 `legacy_import`、来源任务和证据哈希，不从 `model.responded` 推断成功。旧评审缺少校验后的成功检查点时重新评审。

新事件包括 `stage.reused`、`checkpoint.saved`、`checkpoint.runtime_recovered`、`artifact.reused`；`job.queued` 记录 resume 来源及复用列表。复用的阶段不伪造模型请求、不再次累加当次 Token 用量。原始调用用量仍在原任务追溯里；新任务统计不是跨任务完整供应商账单。

## 故障与存储边界

- 服务启动仍将活动任务标为中断、释放单文档锁，由用户选择继续或重跑，不自动发出付费调用。
- 请求已发出、供应商结果未知且无完整持久检查点时，继续执行会重新调用该阶段，可能产生额外费用；不承诺 exactly-once 或从半条模型响应续写。
- 模型节点检查点与业务数据库是两个持久化边界。已完成节点可以弥补后续业务提交失败的窗口；响应返回但节点本身未落盘的窗口仍可能重调。
- 原生节点输出只使用可序列化字典，避免依赖 Python 业务对象的反序列化。阶段证据读取校验 SHA-256。
- 备份必须包含业务数据库与 `.checkpoints` 数据库及各自 WAL。建议停服务后备份整个数据目录。删除原生检查点会降低恢复粒度，不能删除业务阶段记录后仍宣称可恢复。
- 仍仅支持单 API 实例，不解决分布式 worker 所有权、自动重试退避或长期记忆；OTel/Langfuse 接入保持在待办。

## 验证

`tests/integration/test_prd_recovery.py` 覆盖分段中途失败后只调用剩余阶段、从头重跑、评审格式失败不重复发布正文、数据库与应用重开、模型节点已提交但业务阶段提交失败、需求变更拒绝继续、连续失败继承检查点、旧事件导入、取消后继续、互斥参数与跨文档拒绝。

另使用独立子进程在 requirements 成功、ux 等待响应时执行 SIGKILL，再重新打开应用：检查中断事件、已完成阶段保留，以及继续执行不再次调用 requirements。使用受控供应商测试，不对用户的失败任务自动发起真实付费调用。


验证结果：全量 115 项 Python 测试通过，Ruff、Mypy、仓库校验、MkDocs 严格构建和 Studio 生产构建通过。Chromium 验证刷新后的两个恢复入口、继续执行仅调用剩余 3 次模型、重新执行完整调用 7 次、来源关联和移动布局，页面无脚本错误。真实供应商恢复质量与小时级负载未在本轮验收中验证。
