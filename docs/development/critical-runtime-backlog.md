## RT-002 · 长任务持久执行

**发现过程与证据**：`PrdWorkflow.start()` 使用 `asyncio.create_task`；任务 JSON 持久化，但可继续执行的协程只存在于内存。关闭页面不会停止任务，重启 Python 进程会失去协程；现可由用户从持久检查点继续，自动领取和恢复仍待实现。这是源码确认的能力边界，尚未做小时级真实任务稳定性压测。

**拟采用技术与嵌入方式**：先把一个工作流的阶段计划、输入对象哈希、阶段输出哈希、执行版本、deadline 持久化，定义 `JobExecutor` 与 `JobRepository` 端口。API 只提交，后台 worker 从仓库领取任务，`PrdWorkflow` 保留智能步骤，禁止把客户端连接作为任务生命周期。

跨天等待、持久定时器或跨服务流程成立后，将外围流程放入 Temporal，模型/工具副作用放入 Activity，单 Agent 仍由 LangGraph 负责。Temporal 的工作流执行具备持久状态与重放机制，但接入仍需要确定性设计和 Activity 幂等。[Temporal 官方文档](https://docs.temporal.io/workflow-execution)

**故障与验收**：任务超出 API 请求时限仍可查询；停客户端与停 worker 分开验证；重启后能识别最后提交的阶段；工作流代码升级有版本策略。所有领取、暂停、恢复和终态通过 RT-001 记录，禁止不计预算地整条重放。

## RT-003 · 中断与断点恢复

**发现过程与证据**：真实生成任务已完成三个分析阶段后写作截断，旧实现只标记失败，没有继续执行契约。较新的任务在第一个分析阶段就截断，需要区分不同失败现场。

**已实现**：LangGraph `AsyncSqliteSaver` 保存模型节点终态，`PrdStore` 事务保存阶段输出、证据与发布标记。继续执行固定原始输入并复用成功阶段；重新执行采用当前输入从头运行。前端显示两个选项及不可恢复原因。支持从有输入快照的旧任务成功事件导入阶段；没有证据不补造。

**验证与边界**：覆盖失败、取消、应用重开、连续恢复、正文发布去重、需求变更拒绝以及 SIGKILL 后继续；供应商结果未知的阶段可能重新计费。自动重试、跨实例租约和任意工具副作用幂等仍待实现。完整过程见 [RT-003 检查点恢复](runtime-issues/003-checkpoint-recovery.md)。

## RT-004 · 失败重试

**发现过程与证据**：Gateway 区分临时不可用与永久拒绝；工作区捕获异常后直接失败。用户重新发起过去没有关联，本期已补 retry_of_job_id。未实现自动退避、Retry-After 或总重试预算。

**拟采用方案**：定义 `RetryPolicy`，在模型/工具调用边界处理可重试的网络失败、429、部分 5xx；使用有限次数、指数退避与随机抖动，尊重供应商 Retry-After。认证、参数错误、明确拒绝、Schema 校验失败不可无差别网络重试。截断或格式修复属于新的内容修订策略，须有单独预算和可观察输入。

**嵌入方式**：包装 ModelGateway；每次调用创建新 span/attempt，保持同一任务 trace_id，记录 retry.scheduled、原因、延迟和 retry.exhausted。先取得 RT-007 配额再发送；不能重试整个 PRD DAG 来修复一次评审请求。

**验收**：本机可控 HTTP 服务按 429→成功、500→超限、401→立即失败、取消退避等序列测试；证明尝试次数有界、等待不占用执行线程、用量按响应累加、历史失败不会被后续成功抹除。

## RT-005 · 并发控制与互斥

**发现过程与证据**：已有数据库事务/expected_revision 防止多页面覆盖；文档 active_job_id 禁止同文档同时写作；`Semaphore(2)` 只限制当前进程。多个 worker 共享数据库时，内存信号量和启动恢复逻辑都不构成跨进程所有权。

**拟采用方案与嵌入**：拆分入队、领取和执行；通过任务仓库原子 claim + lease_owner + lease_until + fencing_token 持有执行权。发布产物时校验 fencing token，拒绝过期 worker 的迟到写入。文档级写锁与模型级并发配额分开，不用一把全局锁串行所有工作。

单机可从短 SQLite 事务领取开始；多实例迁移 PostgreSQL 时，可用 `FOR UPDATE SKIP LOCKED` 为队列消费者跳过已锁定的行，但不把它用作普通一致性读的替代。[PostgreSQL SELECT](https://www.postgresql.org/docs/current/sql-select.html)

**验收**：两个执行者抢同任务只有一个成功；租约过期后旧 worker 的发布被拒绝；不同文档能并行；取消、重试、重启与发布竞争不产生重复版本。尚未完成该压力测试。

## RT-006 · 异步 I/O 与取消

**发现过程与证据**：API 以 202 返回任务；模型通过 `asyncio.to_thread(urllib)` 调用。取消协程并不能杀掉已发出的阻塞线程；SQLite 读写又在 async 请求中同步执行，且读操作也使用 BEGIN IMMEDIATE。并发量变大时存在事件循环被阻塞、线程占用与写锁竞争风险，尚未测量生产影响。

**拟采用方案**：将 HTTP 换成可取消的异步客户端适配器，设置 connect/read/total 超时和连接池上限；保留 Gateway 协议。数据库采用专用有界执行池或异步适配器，读事务与写事务分开，禁止在等待模型时持有数据库事务。

**嵌入方式**：变化限定在 Model Gateway 和 Repository；工作流仍 await 协议。客户端停止、服务关闭、超时分别产生不同事件。连接取消只证明本地释放资源，供应商结果仍可能未知。

**验收**：使用慢响应服务、断流和连接占满模拟，监控 event-loop lag、线程/连接数量、取消时延；大量查询期间健康检查可返回，已取消任务不得继续发布。

## RT-007 · 限流与预算

**发现过程与证据**：现有上下文/最大输出 Token 可配置，但 Semaphore 不是 RPM/TPM 限流；没有跨任务的供应商配额、用户成本上限或 Retry-After 驱动的调度。429 目前只记录失败。

**拟采用方案**：区分模型并发数、单位时间请求数、Token 预算与费用预算。发送前申请额度，响应后按供应商用量结算；失败但费用未知保留占用或按策略核对。单实例先用单调时钟令牌桶；多实例以 Redis 原子脚本实现共享额度，数据库保存配额账本。

**嵌入方式**：在 TracedModelGateway 和实际 Gateway 之间加入 `RateLimitedGateway`，任务池在额度可用时再分配执行资源；不要让大量协程占着槽位睡眠。记录 rate_limit.wait、budget.reserved/settled、拒绝原因和 next_eligible_at。配额不足与模型失败要分开显示。

**验收**：固定窗口负载、突发、并发争抢和取消释放测试；超预算任务不发模型请求；重试也消耗配额；使用受控时间避免等待真实分钟来测试算法。Redis 失效时有明确策略，不能自动无限放行。

## RT-008 · 有界任务池与背压

**发现过程与证据**：每次 POST 都先 `create_task`，信号量只限制执行中数量，不限制等待协程数。`tasks` 字典可能随提交量无限增长；没有 max_pending、队列满反馈或按文档/用户配额。这是静态检查确认的风险，不伪造 OOM 事故。

**拟采用方案**：使用有界队列和固定 worker 数；入队前检查全局/文档/用户限制。持久入队与 outbox 在同一事务提交，后台 dispatcher 将可执行任务送入内存工作池；收到成功入队响应后，不得因进程重启静默丢任务。

**嵌入方式**：用 `JobPool` 替代 workflow.start 中无界 create_task。API 在满队列时返回明确 429/503 及可重试提示，不创建无法执行的孤儿 job；或显式接受为持久等待，二者契约必须选定。任务列表显示排队而非伪装执行。

**验收**：提交超过容量时内存/协程数量有界、拒绝可解释；取消排队任务释放位置；重启后无丢单；退出时停止入队、等待安全点或写中断记录。

## RT-009 · 调度器与租约

**发现过程与证据**：当前只是事件循环加信号量，缺少独立的任务领取、到期重试、租约心跳和孤儿任务处理。旧 Go Runtime 核心实现存在于仓库，但尚未成为正式 PRD 工作区的执行所有者。

**拟采用方案与嵌入**：定义任务状态机与 scheduler tick；根据 dependencies_ready、not_before、额度和 worker 能力选择任务，再以仓库原子 claim 领取。加入 owner、heartbeat、lease_expiry 与 attempt。Python 先建立可测语义，后续通过现有 Runtime 契约对接 Go 调度服务，避免 Python/Go 同时拥有状态写权限。

延迟任务可以放在数据库索引或 Redis sorted set 中按 next_eligible_at 管理；排序集合提供按 score 排序的数据结构，但可靠领取、幂等和故障恢复仍由本系统设计。[Redis sorted sets](https://redis.io/docs/latest/develop/data-types/sorted-sets/)

**验收**：冻结/推进时钟测试未来任务不会提前执行；worker 死亡后租约过期可被重新领取；时钟漂移不绕过 fencing；调度器重复 tick 不产生重复执行；审计事件区分等待依赖、等待配额、等待 worker。

## RT-010 · 优先级排序与公平性

**发现过程与证据**：现有请求没有 priority、deadline 或队列权重；信号量的唤醒行为不是产品定义的优先级。此项尚无线上饥饿案例，仅确认缺少能力。

**拟采用方案**：服务端定义有限优先级，不允许客户端无限自抬级别。基础排序采用 priority、eligible_at、created_at、稳定 task_id；加入 aging 与用户/项目轮转，避免低优先级或大任务永久饥饿。截止日期和费用额度分别作为约束，而不是混成不可解释分数。

**嵌入方式**：调度器通过 `SchedulingPolicy.rank()` 生成可解释候选顺序；持久化策略版本与排序原因。在执行前重排等待任务；不强制中断已发出的模型请求抢占资源。将 queue_position 标明为动态估计。

**验收**：固定输入输出排序稳定；持续高优先级流量下低优先级在设定上限内获得机会；同级按明确规则排序；取消/重试后不会无成本跳队；每个排序决策可追溯。

## RT-011 · 持久记忆与来源管理

**发现过程与证据**：原参考内核使用 `InMemoryMemoryStore`，正式 PRD 工作区固定保存简报和来源，但未形成跨文档知识与用户偏好记忆。不应把文档持久化、模型上下文和长期记忆称为同一能力。

**拟采用方案**：分开运行工作记忆、文档知识、用户明确确认的偏好。结构化事实、来源版本、权限和失效时间放 PostgreSQL；全文/向量检索通过适配器接 Qdrant，命中内容仍回查权威来源。生成推断不能未经确认就变成全局事实。

**嵌入位置**：实现现有 MemoryStore 端口的持久适配器，在 Context Builder 前按权限检索、排序和预算。记录 memory.retrieved 的对象 ID、版本、来源、相关度和取用片段；在写入时记录谁确认、何时失效、冲突如何处理。输入快照固定当次实际取用记忆，后续更新不会改历史运行。

**验收**：跨进程可读、跨用户不可串读；来源删除或过期后停止召回；更正事实覆盖当前知识但不改历史证据；相互矛盾的记录标明冲突；检索失败不能伪造“已参考历史资料”。
