# 问题与解决记录

本文持续记录 NexusOS 在**开发、集成、部署和实际使用**过程中遇到的工程问题，以及对应的定位过程、解决方案、验证结果与遗留风险。它不是理想化的功能清单，也不把尚未发生的问题写成“线上事故”。

问题来源分为四类：

- `开发测试`：由单元测试、集成测试或代码审查实际发现；
- `场景验证`：在 Nexus PRD 等参考工作流中实际复现；
- `基准测试`：在可重复数据集或规模压测中观察到；
- `部署运行`：在本地 VM、容器、预发布或生产运行中观察到。

每条记录都必须保留首次发现时间。后续方案变化直接追加处理记录，不覆盖原始判断；如果最终证明根因不同，应明确更正。

## NX-001 · Skill 清单缺省字段触发类型校验失败

- **首次发现**：2026-05-24
- **来源**：开发测试
- **现象**：加载未声明 `examples` 的合法 Skill 时，清单解析失败；显式写入空列表则可以通过。
- **影响**：最小 Skill 包无法按约定加载，作者被迫填写没有业务意义的占位字段。
- **定位过程**：使用最小清单夹具复现，确认 YAML 内容本身合法；继续检查发现模型默认值是元组，而字段校验器只接受列表。
- **根因**：内部不可变默认值与外部 YAML 数组契约不一致，默认值也经过了同一类型校验。
- **解决方案**：把外部集合字段默认值统一为空列表，在模型构造后再转换为不可变表示；增加“省略可选集合字段”的回归用例。
- **验证方式**：最小清单、完整清单、错误类型三组测试均通过，版本化仓库可以同时加载多个 Skill 包。
- **预防措施**：清单模型的默认值必须使用与序列化格式一致的类型；新增字段同时提供最小契约测试。
- **遗留风险**：未来接入 Pydantic 或其他 Schema 框架时，默认值校验策略可能变化，需要复用同一夹具重新验证。

## NX-002 · 测试发现命令成功退出但实际执行 0 项

- **首次发现**：2026-06-12
- **来源**：开发测试
- **现象**：`unittest discover` 返回退出码 0，但输出为 `Ran 0 tests`。
- **影响**：CI 或开发者可能把“没有收集到测试”误判为测试通过，让回归问题进入后续分支。
- **定位过程**：指定单个测试文件可以执行，目录发现模式无法递归；检查包结构后发现测试目录缺少包标记。
- **根因**：当前 Python 发现规则要求递归目录可导入，而测试目录没有 `__init__.py`；同时校验流程只检查退出码，没有检查收集数量。
- **解决方案**：为测试目录补充包标记，固定仓库级测试命令，并增加架构测试保证关键测试模块可发现。
- **验证方式**：同一发现命令由 0 项恢复为 13 项且全部通过；后续新增套件继续使用同一入口。
- **预防措施**：CI 日志必须显示测试数量；不得用单纯的退出码 0 作为“测试已覆盖”的证据。
- **遗留风险**：如果未来迁移 pytest，需要重新设置最少收集数或等价保护。

## NX-003 · 一次性加载全部 Skill 导致上下文被指令淹没

- **首次发现**：2026-06-12
- **来源**：场景验证、基准测试
- **现象**：在 PRD 工作流中把所有 Skill 正文拼入提示词后，真正的用户需求与中间产物占比明显下降；目录扩大时 Token 线性增长。
- **影响**：模型成本和延迟上升，注意力被无关规则分散，长目录最终会超过上下文窗口。
- **定位过程**：分别运行 All Skills、关键词选择和混合路由，记录选中 Skill 数、指令 Token、Recall@K 与排序解释。
- **根因**：Skill 发现和 Skill 正文加载没有分层；系统把“可能有用的能力”误当成“本次必须注入的指令”。
- **解决方案**：采用三级渐进加载：启动阶段只读元数据，路由后读取 `SKILL.md`，只有执行需要时才加载参考资料；增加 Token 预算器和确定性裁剪。
- **验证方式**：版本化路由数据集与 100～10,000 Skill 合成规模测试可以重复比较质量和 Token；当前小样本显示相关 Skill 可被保留，无关正文不再进入上下文。
- **预防措施**：路由变更同时报告质量和 Token，禁止只用 Token 降幅证明方案有效。
- **遗留风险**：合成负样本不等同真实困难样本；进入生产前仍需用匿名化真实查询做离线回放。

## NX-004 · 本机缺少多语言与容器工具链

- **首次发现**：2026-07-18
- **来源**：开发环境
- **现象**：当前 Windows 开发机可以运行 Python，但找不到 Go、Cargo/Rust、Node.js 和 Docker 命令。
- **影响**：Go Runtime、Rust Router、TypeScript Studio 和 Compose 无法在本机完成编译或启动验证。
- **定位过程**：检查命令路径与版本，区分“代码未通过”与“验证工具不存在”，避免把静态检查写成编译成功。
- **根因**：开发机只配置了 Python/Git 基础环境，多语言实现先于统一构建环境落地。
- **解决方案**：保留可运行的 Python 规范实现；本机先执行契约、源码结构和 YAML/JSON 校验；后续由固定版本的 Linux CI 承担 Go、Rust、Node.js 和容器构建。
- **处理记录（2026-08-23）**：已增加固定版本的跨语言 CI 矩阵和仓库级验证器，覆盖 Go Race Detector、Rust Clippy、Studio 类型/生产构建、MkDocs 严格构建与 Compose 展开。
- **验证方式**：Python 回归和仓库级契约检查可在本机执行；缺少工具链的组件仍明确标记为“待首次远程 CI 验证”，不因工作流文件存在就宣称已经编译。
- **预防措施**：提交新语言组件时必须同步增加 CI Job，并固定编译器版本。
- **遗留风险**：CI 尚未建立前仍存在平台编译差异，本问题维持“已缓解”而不是“已解决”。

## NX-005 · 远程任务重试可能重复执行有副作用的工作

- **首次发现**：2026-07-18
- **来源**：集成测试、故障推演
- **现象**：客户端超时后重发任务，首次请求可能已经执行成功；第二次请求会再次调用写数据库、发消息或外部工具。
- **影响**：产生重复工单、重复通知、重复计费或不一致的运行状态。
- **定位过程**：用并发请求和相同任务输入复现，发现仅依赖 `task_id` 无法区分合法的新尝试与网络层重复提交。
- **根因**：远程 Runtime 定义了重试次数，却没有把幂等性纳入传输契约和结果缓存。
- **解决方案**：任务契约强制携带 `run_id`、`task_id` 和 `idempotency_key`；Go Runtime 合并进行中的相同请求并复用已完成结果；MCP Gateway 在租户范围内重复检查工具调用键。
- **验证方式**：并发重复请求测试只调用一次实际 Handler，所有调用者得到同一结果；数据库对工具幂等键增加唯一约束。
- **预防措施**：有副作用的 Tool 不允许依赖自动生成且不可追踪的键；重放操作必须显式选择复用或创建新键。
- **遗留风险**：单进程内存缓存不能覆盖实例重启和多副本，生产部署需要 Redis 或 PostgreSQL 持久化幂等记录。

## NX-006 · 固定 PRD 分数无法反映真实产物质量

- **首次发现**：2026-07-26
- **来源**：场景验证
- **现象**：演示流程无论输入和生成内容如何都给出固定质量分，缺少核心章节的 PRD 也可能显示“通过”。
- **影响**：质量门失去可信度，Replanner 没有具体的修订目标，用户无法解释分数来源。
- **定位过程**：构造缺少目标、用户流程和验收标准的产物，比较固定评分与人工检查结果。
- **根因**：早期端到端样例用常量代替了评估端口，评审结果没有结构化维度和阻断规则。
- **解决方案**：引入版本化 Rubric，分别计算清晰度、完整性、可行性、一致性和证据覆盖；核心章节缺失优先阻断，并输出具体失败维度。
- **验证方式**：完整夹具达到阈值，删除任一核心章节后稳定失败；同一产物重复评估结果一致。
- **预防措施**：演示桩不得进入正式质量字段；未来模型评审只能补充判断，不能覆盖确定性阻断项。
- **遗留风险**：确定性规则可能鼓励格式满足而不是真实业务价值，需要通过人工盲评校准权重。

## NX-007 · 可选 HTTP 与容器依赖在当前开发机不可用

- **首次发现**：2026-08-01
- **来源**：部署验证
- **现象**：FastAPI 未安装，Docker 命令不可用，无法在当前开发机直接启动 HTTP API 和 Compose 栈。
- **影响**：核心工作流可以进程内运行，但网络边界、镜像健康检查和基础设施联调不能在本机形成完整证据。
- **定位过程**：分别检查 Python 可选依赖导入和 Docker 客户端；API 序列化测试可运行，服务启动失败是环境缺失而非业务异常。
- **根因**：核心包刻意保持轻依赖，而本机没有安装 `api` 可选依赖与容器运行时。
- **解决方案**：把 FastAPI 保持为可选 extra，核心测试不依赖 Web 框架；使用 PyYAML 和契约测试验证 Compose 配置；把真正的启动探针交给后续 CI 集成环境。
- **处理记录（2026-08-23）**：CI 增加 `api` 可选依赖安装、MkDocs 严格构建、Studio 生产构建和 `docker compose config`，先覆盖构建与配置层证据。
- **验证方式**：核心 Orchestrator 和 API 响应映射测试通过，Compose YAML 可解析；首次远程 CI 与真正的容器健康检查仍待外部环境执行。
- **预防措施**：文档把“源文件校验”“构建通过”“服务可启动”作为三种不同证据，不混用结论。
- **遗留风险**：依赖版本冲突和容器启动顺序尚未被真实运行覆盖，本问题保持“已缓解”。

## NX-008 · 无界 Reflection 可能反复重写并消耗预算

- **首次发现**：2026-08-15
- **来源**：场景验证、故障推演
- **现象**：评审失败时若只返回“继续优化”，写作 Agent 会重复生成整份 PRD；质量没有提升时流程没有稳定终点。
- **影响**：Token 和时间不可控，已正确的章节被反复修改，Run 可能长期占用 Worker。
- **定位过程**：让评审持续返回相同失败维度，观察无上限重试策略会重复构造相同任务图。
- **根因**：Reflection 被实现为自由文本循环，没有修订范围、轮次预算和最终状态。
- **解决方案**：把失败维度映射成 Research、Requirements 或 Technical 修订任务，只重走受影响路径；默认最多两轮，仍不通过则把 Run 标记为 `blocked`。
- **验证方式**：测试覆盖一次修复后通过和持续失败达到上限两条路径；每轮任务 ID、评审分与事件均可追踪。
- **预防措施**：任何循环型 Agent 能力必须同时声明最大轮次、最大 Token、退出状态和人工接管点。
- **遗留风险**：当前依赖维度级映射，尚不能精确判断段落级证据依赖，可能执行多余修订。

## NX-009 · 连接池复用可能造成数据库租户上下文串用

- **首次发现**：2026-08-16
- **来源**：安全审查
- **现象**：如果使用会话级变量保存租户 ID，连接归还池后可能被另一租户复用；遗漏 `WHERE tenant_id` 的查询也可能读取跨租户数据。
- **影响**：造成高严重度的数据越权和审计污染。
- **定位过程**：审查所有带 `tenant_id` 的表和连接生命周期，发现应用过滤与会话级设置都依赖每个调用点正确清理。
- **根因**：租户隔离只停留在应用约定，没有数据库级默认拒绝；连接池把物理会话复用于多个逻辑请求。
- **解决方案**：所有租户表启用并强制 PostgreSQL RLS；每个事务使用参数化 `set_config(..., true)` 写入事务级租户上下文；平台迁移使用独立角色。
- **验证方式**：架构测试枚举租户表并检查 Enable、Policy、Force 三项；Python 适配器拒绝非 UUID 输入并只生成参数化调用。
- **预防措施**：数据访问必须在显式事务中进行；禁止使用会话级 `SET`；新增租户表时架构测试会要求同步增加策略。
- **遗留风险**：当前开发机没有 PostgreSQL 容器，真实连接池的跨事务集成测试尚未执行，因此状态为“观察中”。

## NX-010 · Studio 无法从内部运行状态稳定构造可解释视图

- **首次发现**：2026-08-22
- **来源**：场景验证
- **现象**：用现有 API 设计运行详情页时，只能获得最终任务状态和选中 Skill ID，无法稳定展示任务标题、依赖关系、路由候选分、排除原因和事件时间线。
- **影响**：界面如果直接读取内部 `NexusState`，会与 Python 实现细节耦合；如果自行拼接数据，又会让 UI 展示与真实决策不一致。
- **定位过程**：逐项对照 Studio 信息架构和 `/v1/prd/runs` 响应，确认问题是缺少面向查询的读模型，而不是单个组件渲染错误。
- **根因**：早期 API 只为同步演示返回最终产物，没有为可观测控制台设计摘要、详情和事件投影。
- **解决方案**：先用独立 TypeScript View Model 和明确标记的演示快照冻结页面需求；随后增加运行摘要、详情和路由/预算投影 API，不导入 Python 内部类型，也不允许 Studio 直读数据库。
- **验证方式**：投影契约测试覆盖任务定义、路由原因、时间和产物；内存存储验证容量淘汰与防御性副本；页面仍显示“演示快照”，样例指标不进入正式监控结论。
- **预防措施**：Studio 新字段必须先进入版本化 API 投影；禁止通过数据库表或内部状态对象绕过服务契约。
- **遗留风险**：Studio 尚未切换到真实 API，进程内投影重启后会丢失；完成前保持“观察中”，并需要补加载、空状态和失败状态测试。

## NX-011 · 外部 Agent 的重复或乱序事件会让任务状态回退

- **首次发现**：2026-08-23
- **来源**：集成测试、故障推演
- **现象**：远程 Agent 完成后，延迟到达的 `working` 事件可能覆盖本地完成态；重复 `completed` 事件又可能让同一产物被消费两次。
- **影响**：Nexus Run 长期显示运行中、重复触发下游任务，或者在已经交付产物后再次计费。
- **定位过程**：按“完成事件先到、旧工作事件后到”和“同一状态重复投递”两组顺序驱动生命周期，确认直接赋值状态无法保持单调性。
- **根因**：外部状态被当成普通字段同步，没有合法迁移表、终态保护和重复事件语义。
- **解决方案**：增加 A2A Task 状态机；只允许显式迁移，四种终态不可回退；相同状态重复事件返回当前投影；产物只能随完成态写入，失败必须携带稳定错误码。
- **验证方式**：自动化测试覆盖完成、等待输入后恢复、终态回退、重复提交、失败错误码和非 HTTPS Agent Card 六类路径。
- **预防措施**：远程适配器不得直接修改 Nexus Task；新协议状态必须先定义映射和迁移测试。
- **遗留风险**：当前未连接真实 A2A Server，跨连接事件序号和多副本并发仍需持久化版本号或条件写保证。

## NX-012 · 首次统一 Lint 暴露跨模块风格漂移

- **首次发现**：2026-08-23
- **来源**：开发测试
- **现象**：新增 CI 后在本地执行同一 Ruff 命令，发现 10 个文件需要格式化、31 个导入顺序、现代化语法、行长或框架规则问题。
- **影响**：直接提交工作流会让 Python Job 必然失败；不同阶段代码风格继续漂移也会增加评审噪声。
- **定位过程**：先运行只读的 `ruff format --check` 和 `ruff check`，区分安全自动修复项、纯格式项与需要人工判断的问题。
- **根因**：项目前期只执行功能测试，虽然 `pyproject.toml` 已声明 Ruff 规则，但没有在每次提交或统一入口中实际执行。
- **解决方案**：使用同一 Ruff 版本完成安全修复和格式化；手工处理 FastAPI Body 推断、类型联合、路由条件简化与长字符串；CI 固定执行格式和 Lint 检查。
- **验证方式**：`python -m ruff format --check .` 与 `python -m ruff check .` 均零错误，完整 Python 测试随后再次执行。
- **预防措施**：Python Job 把格式和 Lint 置于测试之前；开发者提交前使用与 CI 相同命令。
- **遗留风险**：当前没有 pre-commit Hook，提交者仍可能到远程 CI 才看到问题，但主分支质量门可以阻止合入。

## NX-013 · Studio 静默使用样例时容易被误认为真实监控

- **首次发现**：2026-08-29
- **来源**：场景验证
- **现象**：API 没有启动时，控制台仍展示完整运行、成功率和 Token 指标，但页面无法说明这些数字来自演示快照。
- **影响**：使用者可能据此判断系统健康或效果，掩盖真实 API 故障，并把样例数据带入演示结论。
- **定位过程**：分别在未配置地址、地址拒绝连接和返回非 2xx 三种情况下检查总览与详情，确认数据本身正常但来源不可见。
- **根因**：首版快照只用于冻结信息架构，没有把数据来源作为页面状态建模。
- **解决方案**：建立 API 优先的数据源适配器，设置 2.5 秒超时；失败时返回快照和错误说明；总览与详情始终显示“实时 API”或“演示快照”，快照模式额外展示黄色告警。
- **验证方式**：未设置环境变量时确定性进入快照模式；所有网络和状态码异常通过同一降级分支返回可见告警；类型适配对未知状态按失败处理。
- **预防措施**：样例、缓存和实时数据必须携带来源；写操作在非实时来源下保持禁用。
- **遗留风险**：当前尚未完成 Node.js 生产构建验证，CI 通过前仍可能存在前端类型或构建兼容问题。

## NX-014 · 长任务在全局上下文充足时仍被分区硬上限拒绝

- **首次发现**：2026-08-29
- **来源**：场景验证、开发测试
- **现象**：Task 分区默认只有总窗口的 8%，当用户原始需求超过该比例时，即使其他分区完全空闲且总输入预算充足，运行仍抛出 `required context does not fit budget`。
- **影响**：详细的企业需求无法进入 Planner/Agent，用户只能人为删减关键约束；提高总窗口也可能仍被固定比例阻断。
- **定位过程**：用 100 Token 总窗口、20 Token 输出预留和约 15 Token 必要 Task 构造最小用例；全局可用 80 Token，但原算法因 Task 上限 8 Token 拒绝。
- **根因**：分类占比同时承担了防挤占和必要内容可用性两种冲突职责，被错误实现为所有片段的硬上限。
- **解决方案**：总输入预算继续作为硬上限；必要片段允许借用未使用分类空间，普通片段仍按分类上限裁剪；报告记录 `borrowed_tokens`。
- **验证方式**：回归测试确认 15 Token 必要 Task 被保留、借用 7 Token、同分区普通内容被裁剪，且总输入不超过 80 Token；真正超过全局预算的必要内容仍失败。
- **预防措施**：修改分区比例时同时覆盖“分区超限但全局可容纳”和“全局不可容纳”两类测试，并监控借用量。
- **遗留风险**：多个必要片段仍按优先级依次占用全局预算；未来需要在入口阶段给出更友好的拆分建议，而不只是抛出错误。

## NX-015 · 模型供应商瞬时故障直接终止整条 Agent 任务

- **首次发现**：2026-08-30
- **来源**：故障推演、开发测试
- **现象**：主模型端点超时、返回 429 或 5xx 时，调用异常直接传播到 Runtime，即使已经配置另一个健康模型也不会接管。
- **影响**：单一供应商抖动使整条多 Agent 运行失败；人工重试会重复前序工作和 Token 消耗。
- **定位过程**：用记录请求的假后端分别注入瞬时不可用和永久请求错误，确认原 Gateway 没有错误分类或后端顺序策略。
- **根因**：统一模型契约只抽象了调用格式，没有抽象目标、数据放置限制和可降级错误语义。
- **解决方案**：增加有序 `ModelTarget` 和 `FallbackModelGateway`；只对瞬时错误切换，每目标最多一次；永久错误立即失败；根据请求数据分类过滤目标。
- **验证方式**：测试覆盖主端限流后切换、永久拒绝不切换、受限数据跳过云端、所有目标故障聚合四条路径，并检查每个后端调用次数。
- **预防措施**：新增适配器必须把供应商错误映射为瞬时不可用或永久拒绝；降级目标需显式声明数据分类。
- **遗留风险**：超时不代表供应商一定未执行，切换可能重复计费；真实供应商遥测和费用对账完成前保持“观察中”。
