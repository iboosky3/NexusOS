# 需求与产品出发点日志

本文持续记录 NexusOS 产品开发的**原始需求、提出背景、设计出发点、验收边界和实现轨迹**。它既是需求文档，也是产品演进日志。

代码描述“现在如何工作”，本日志回答“为什么要这样改”。后续产品功能、交互和信息架构变更必须先关联已有需求编号；没有对应条目时，先追加需求，再开始实现。

## 记录规则

1. 保留提出者的原话或忠实摘录，不用后来的实现方案覆盖最初动机。
2. 每条需求使用稳定编号，记录日期、来源、状态、问题、目标、验收标准和明确不做的范围。
3. 实现过程中只追加方案调整、验证结果、关联提交和遗留项；需求发生变化时记录变更原因，不改写历史。
4. 一次代码改动可以关联多条需求，但必须说明本次实际覆盖的范围，不能以局部实现宣称整条需求完成。
5. 只有相关交互、数据链路和自动化验证都完成后，状态才能改为“已实现”；界面占位、设计文档或单独原型均不算完成。

## REQ-001 · 将项目工作区的组件化原型体验统一到 PRD Studio

- **首次提出**：2026-09-21
- **来源**：用户实际使用反馈
- **状态**：部分实现
- **关联页面**：`/prd-studio`、`/projects/{projectId}/workspace`

### 原始出发点

> 我觉得 `/projects/{projectId}/workspace` 这种布局更合理，点击原型组件后就能够在右侧看到可以编辑的属性，还能和 AI 对话。而且原来的原型设计组件很简陋，没有设计感。应该把 `/projects/{projectId}/workspace` 的功能并入到 **PRD Studio**。
>
> 原型页面整体显示以组件、画布为中心。编辑模式可以是点击组件后显示对应的属性框进行修改；属性框在视图中可以选择显示或者隐藏，所有的界面功能都应该具备此功能。也可以点击组件后，让 AI 修改对应的组件；也可以选择代码编辑模式，分屏后显示代码和预览，点击组件时对应的代码高亮，然后编辑相关参数。
>
> 以后每次改动都写最初的出发点，算是需求文档，不断开发，不断罗列需求文档。

### 问题定义

当前 `/prd-studio` 已有文档写作、任务执行和原型插件能力，但原型编辑体验与工作区整体布局割裂，组件视觉和编辑反馈不足。`/projects/{projectId}/workspace` 具备更清晰的“资源—画布—上下文面板”结构，却仍是独立入口和本地演示实现。两套入口并存会造成能力重复、数据不一致和用户认知负担。

### 目标能力

1. 以 PRD Studio 作为统一入口，吸收项目工作区的三栏布局和组件选择体验，不再维护两个相互独立的产品入口。
2. 原型区域以组件库和画布为核心，提升组件、排版、状态和交互反馈的视觉质量。
3. 点击画布组件后，右侧展示该组件的属性、样式和交互设置；修改后立即反映到画布与预览。
4. 属性、AI、资源、运行记录等辅助面板都允许按需显示、隐藏和恢复，不为当前任务无关的功能固定占位。
5. AI 对话携带当前选中组件、页面、原型版本和相关 PRD 上下文，可针对该组件提出修改并在用户确认后应用。
6. 提供代码编辑模式；代码与预览分屏显示，画布选中组件后定位并高亮对应代码，代码修改能更新同一份原型状态。
7. 保留现有 PRD Studio 的文档、版本、运行、追溯、模型工作流和原型持久化能力，合并不能造成既有能力回退。

### 实现约束

- 画布、属性面板、AI 修改和代码编辑必须操作同一个结构化原型数据源，不能长期依赖互相替换整段 HTML。
- 每个组件需要稳定 ID，用于选中、属性修改、代码定位、AI 上下文、截图引用和版本追溯。
- 面板显示状态与尺寸需要可恢复；隐藏面板后不得丢失未保存内容或当前组件选择。
- AI 修改必须展示目标组件和变更范围，不得静默覆盖整页原型。
- 原型组件需要统一设计令牌、状态和响应式规则，不能只增加无样式的 HTML 控件。
- 合并应复用现有持久化文档和原型能力，避免继续扩展只保存在浏览器 `localStorage` 的平行数据模型。

### 初步验收标准

1. 用户从 PRD Studio 内进入原型设计，无需手工访问项目工作区 URL。
2. 用户点击任一画布组件，右侧属性面板显示与该组件一致的可编辑字段；关闭并重新打开面板后选择仍然有效。
3. 修改属性后，组件树、画布、预览和保存结果保持一致；刷新页面后从持久化数据恢复。
4. 用户可针对选中组件发起 AI 修改，提交前能看到目标组件和拟应用的变更。
5. 用户切换到代码模式后看到代码与预览分屏；点击组件能高亮对应代码位置，修改后预览和属性面板同步。
6. 所有主要辅助面板都有明确的显示、隐藏和恢复入口，并通过键盘与窄屏场景验证。
7. 原型组件具有一致的颜色、排版、间距、交互状态和至少桌面／移动两种画布表现。
8. 原有 PRD 创建、保存、版本、生成、评审、追溯和截图能力继续通过回归测试。
9. 合并完成后，旧项目工作区被重定向、迁移或明确标记为兼容入口，不再形成第二套独立数据源。

### 当前边界与待决策项

- 代码模式目前采用结构化 JSON 文本编辑；若未来引入 Monaco 或 CodeMirror，需要验证包体积、可访问性和组件级高亮。
- Puck 设计树是新功能唯一原型数据源；不承诺任意 HTML/React 代码的可逆转换，JSON 修改需要验证后应用。
- 旧 `/projects/{projectId}/workspace` 保留浏览器本地草稿作为历史入口，尚未实现将本地 HTML 草稿迁移到 PRD Studio 的导入工具。
- 对局部 AI 补丁还需要进行实际浏览器交互验收；目前自动化覆盖后端契约、类型检查与生产构建。

## REQ-002 · 原型中央区域只保留设计操作，AI 请求统一在右侧对话

- **来源**：用户对重构后原型布局的反馈
- **状态**：部分实现

3. 手工添加页面、导入原型图、编辑画布、保存、确认与截图不受影响。
4. 页面空状态和使用文档只指向实际存在的 AI 入口。

## REQ-003 · 页面元信息移出原型画布上方

- **状态**：部分实现

> 页面名称 、 页面与交互说明 这些都不应该占用中间的原型编辑区域，不然编辑区复杂还不够大

4. 页面名称修改后，页面导航、画布标题与 AI 上下文同步；保存、确认和截图校验保持原状。

## REQ-004 · 将原型和 PRD 拆为可协作的专注插件工作区

- **首次提出**：2026-09-21
- **来源**：用户对原型设计区密度、编辑专注度和工具边界的反馈
- **状态**：实现中
- **关联页面与模块**：`/prd-studio`、`/projects/{projectId}/workspace`、原型设计插件、PRD 编写能力、工作台侧边栏、Agent 工作流

当前状态更新：部分实现，已交付独立入口、插件编辑入口、工作流动作分工与显式交接；通用 Agent 消息协议和自动协作尚未完成。

### 原始出发点

> 1、需要一个在浏览器打开的按钮，现在“保存设计方案”、“导入原型图”、“预览原型”、“确认并嵌入PRD”、"原型设计方案文档"、“方案列表”等都占据了中间的位置，显得很复杂又占用编辑空间，需要优化。原来“[http://172.23.17.15:3000/projects/demo-project/workspace](http://172.23.17.15:3000/projects/demo-project/workspace)”的编辑区域就很干净。可以把原型设计做成一个单独的插件（支持Agent，把编写PRD也做成一个插件，支持Agent，这样二者就可以交互了），支持添加到左侧侧边栏快速启动，然后增加隐藏侧边栏功能，全屏编辑功能，这样就能和projects/demo-project/workspace”的界面接近，有更干净跟相关的编辑界面，更能够集中精力构思原型。这个原型插件（支持Agent）只是做原型，通过交互与生成PRD的插件（支持Agent）配合生成完整的PRD。

### 问题定义与设计出发点

当前原型设计入口同时承担画布、保存、导入、预览、确认、嵌入 PRD、归档方案和页面列表。操作虽然齐全，但常驻在画布上方或周围，缩小画布并分散注意力。旧项目工作区的独立编辑视图更接近用户期望；然而它使用本地草稿，不能直接作为新原型的长期数据源。PRD Studio 中原型与 PRD 也仍以一个页面内的标签耦合，不利于给各自的 Agent 明确职责。

### 目标能力

1. 原型提供“在浏览器打开”入口，进入可直接访问、可分享同一已保存文档上下文的专注工作区；新入口不是旧本地工作区的第二套数据模型。
2. 原型画布作为主体。保存、图片导入、预览、确认、嵌入 PRD、方案归档及页面列表分别收进菜单、可折叠侧栏或属性区域，避免在中央堆叠按钮和长文档。
3. 原型作为单独可启用的插件／工具工作区，能从左侧侧边栏快速启动；PRD 编写也有独立入口，二者使用相同文档 ID、版本与权限边界。
4. 左侧导航／侧栏可显示、隐藏、恢复；提供专注／全屏编辑模式，并保留退出入口和键盘路径。
5. 原型 Agent 只处理原型页面、组件、交互、截图与原型建议；PRD Agent 负责需求澄清、正文编写、修订和评审。两者通过版本化的原型快照、页面说明和显式交接动作协作，而不是任意修改彼此的私有状态。
6. 从原型工作区交接 PRD 时，应明确是否已确认原型、是否包含最新截图、目标文档版本和未保存变更；PRD 工作流只能读取合法且已确认的原型上下文。

### 实现约束与风险

- 保留 NexusOS 编排内核、现有 Puck 结构化原型、PRD 文档持久化、版本历史、截图和审计链路；不得复制成长期平行的 `localStorage` 项目模型。
- “在浏览器打开”若新窗口只能读取已保存版本，必须明确提示或先安全保存；不得让用户误以为未保存草稿已在两个标签页同步。
- 工具入口与真正的 Agent 插件生命周期要分层：侧栏快捷入口可先交付，但不能把页面链接或静态 manifest 冒称已经完成 Agent 间协作。
- 独立工作区和当前 PRD Studio 需要处理同一文档的并发编辑、版本冲突、恢复与回退；跨窗口的未保存草稿不能静默覆盖服务器版本。
- 旧 `/projects/{projectId}/workspace` 仅作为布局参考，后续迁移或兼容方案需要单独验证。
- 全屏模式应兼容浏览器 Fullscreen API 不可用或被拒绝的情况；仍应支持应用内专注模式。

### 分阶段验收

1. **界面减法**：原型区域第一屏只突出页面切换、画布与少量核心操作；次级操作可被发现并恢复，功能无回退。
2. **浏览器独立入口**：从原型工作区打开独立地址时，已保存内容正确载入；未保存状态明确阻止或安全处理；返回 PRD 入口清晰。
3. **工作区控制**：左栏快捷启动、隐藏／恢复侧栏与专注模式有可访问按钮，刷新后按设计恢复偏好；窄屏不会丢失操作入口。
4. **插件边界**：原型工具与 PRD 工具各有声明式能力、独立界面入口与可测试的 Agent 命令契约；启用／禁用不删除数据。
5. **Agent 交接**：原型确认后交接给 PRD Agent，后者能读取同一文档的原型快照、说明与截图，并能报告所用版本；错误版本、未确认内容和跨窗口冲突被拒绝或要求确认。
6. **回归**：手工设计、AI 局部建议、预览跳转、保存、导入、截图、嵌入、PRD 生成／修订、历史版本均通过自动化与浏览器交互验证。

### 当前决策与边界

- 第一阶段先交付干净的原型编辑表面、独立入口和显隐控制；保留既有 PRD 数据链路。
- 原型／PRD Agent 的真正插件接口与跨 Agent 交接属于后续阶段；未实现前只把现有能力标注为现有工作流，不宣称完成整个需求。

## REQ-005 · 可关闭编辑器标签与通用 Agent 插件工作台

- **来源**：用户纠正产品核心思想
- **状态**：部分实现

### 原始出发点

> 菜单栏下边的：“需求简报”、“原型设计”、“房屋设计md”，这些应该都是能够关闭的。另外原来的核心思想是按照vscode的思想，软件本身做基础功能，然后通过组合插件的方式，搭建自己的工作区。现在编写PRD和构建原型就是两个很好的插件，我希望能做成支持Agent功能的插件。你看看现在还需要做什么调整

### 本次实现与验收

所有已打开标签都可关闭，关闭非当前标签不跳页，关闭当前标签激活相邻标签，全部关闭后显示可重新打开工具的空工作区。关闭标签仅改变界面状态，不删除文档或停止任务。原型编辑器在切换／关闭标签后保留当前会话内的编辑状态，包括未应用的 JSON 草稿。刷新、保存后的文档版本重新载入及插件禁用的草稿生命周期仍需独立完善。

验证：前端类型检查通过；浏览器使用模拟 API 验证关闭非当前／当前／全部标签、重新打开 PRD、保留未应用原型 JSON，以及无活动编辑器时禁用 AI 提交。原型编辑器首次打开时才加载，其后隐藏保留当前会话状态。

### 当前架构证据与调整顺序

1. **基础工作台**：`Workbench` 已封装菜单、快捷栏、分屏、全屏和命令搜索，但标签列表和大量业务入口仍写死在 `StudioWorkspace`。先把编辑器打开／关闭／激活抽成通用状态管理，再由插件贡献编辑器、菜单、快捷入口和资源视图。
2. **插件生命周期**：当前 `WorkbenchExtension` 只有 manifest 与组件加载器，启用状态只存本机。需补 `activate(context)`、`deactivate()`、注册与释放机制，并保存工作区的启用插件、布局和打开资源；多项目工作区必须有独立身份。
3. **Agent 接口**：`agentActions` 只是前端动作白名单；澄清、组件建议直接在 Assistant 请求，重启／恢复走宿主 `w.start`。需要统一的 Agent 注册、输入／输出 schema、上下文范围、进度、取消、重试、审批及服务端能力校验，所有入口通过同一调用层。不能仅把对话标题改成 Agent 就算实现。
4. **资源解耦**：原型目前仍存于 PRD Brief，独立原型工作区仍依赖 `usePrdStudio`。需要通用资源 ID、类型和版本 API，将原型项目与 PRD 文档分为独立资源；旧文档需兼容读取与明确迁移，不能直接拆表丢数据。
5. **插件间协作**：当前交接由宿主截图、拼接正文、保存后跳页。应改成版本化产物契约（来源插件／资源／版本、页面说明、截图引用、确认状态），由 PRD 插件消费并记录来源；需要稳定错误状态与并发冲突处理。
6. **边界回归**：验证插件禁用时所有 Agent 入口一致失效、编辑草稿可恢复、关闭编辑器后任务继续运行、没有安装业务插件时基础工作台仍可使用。现有代码尚不能宣称满足这些完整边界。

### 人类友好与效率建议

- 关闭标签不等于删除文档；草稿状态继续显示在工作台，重新打开直接回到编辑现场。
- 插件贡献自己的相关命令与 Agent，上下文随当前编辑器切换；全空工作区不应继续提供可发送的隐含 PRD 对话。
- 后续支持恢复关闭的标签、工作区布局预设和“仅显示当前工具相关命令”，减少重复点击与无关入口。

## REQ-006 · Agent 插件工作台独立方案与分阶段实施
