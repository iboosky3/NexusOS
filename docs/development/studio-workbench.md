# Studio 通用工作台与工具接入

## 纽带系统核心思想 · 所有工具界面的首要设计约束

> **以用户任务为中心，由 AI 分析需求，从已注册、可执行的能力与组件中按需组装工作界面。界面只呈现当前任务需要的组件；同一功能只有一个主要入口，不重复铺设，不为无关能力或未来功能占位。**

**保留软件式工作台外壳：菜单栏、按需工具栏、左侧管理区、中间编辑区、右侧 AI、底部状态栏。按需组装约束的是任务内容、展开层级和辅助面板，不是删除软件外壳或改成普通表单页。**

PRD 在该外壳中组装简报、原型设计、正文编辑和 AI 协作；左侧管理资料与能力，绘图、版本和追溯按需打开。新增任务应复用组件并选择合适组合，不复制一套固定、包含所有功能的工作台。

这是纽带系统的核心设计原则，不是单次界面美化要求。组件应随任务需要出现和退出，已输入的数据和执行中的任务必须保留。

## 设计验收约束

- 保留稳定的软件导航、编辑和状态外壳；每个业务组件必须能说明它对当前任务的用途，无关业务内容不挂载、不占位。
- 同一动作只有一个主要操作位置；快捷键和命令搜索可映射该动作，不再铺设第二套常驻按钮。
- 材料、绘图、版本、追溯和能力检查按需打开，完成或关闭后归还编辑空间。
- 任务组合来自已注册组件及其能力、输入输出、状态与依赖；AI 只提出组合计划，不注入任意可执行界面代码，也不绕过现有权限和执行约束。
- 隐藏、切换或重组组件不得丢失草稿、对话、媒体或服务端执行现场。
- 当前 PRD 采用明确的任务组合规则。跨任务的 AI 需求分析与组件组合规划是目标架构，不能把静态规则或菜单切换宣称为已实现的 AI 动态组装。

## 页面边界

首页负责选择工具，“编写 PRD”使用带 `target="_blank"` 和 `rel="noopener noreferrer"` 的链接打开 `/prd-studio`。首页不采集、预填或通过 URL 传递产品想法；文字入口仅按 PRD 相关关键词匹配已开放工具，不是模型意图识别服务。

`/prd-studio` 是新版工具页面，`/prd` 保留。两者使用同一套文档、任务、版本和追溯 API；新版浏览器草稿有独立的 `sessionStorage` 命名空间。旧版只提供基础 Markdown 展示，不承诺解析新流程图格式。`AppShell` 根据路径让 Studio 使用自己的全屏布局，避免旧导航在覆盖层下仍能获得键盘焦点。

## 组件分层

| 层 | 文件（相对 `apps/studio`） | 责任 |
| --- | --- | --- |
| 通用容器 | `components/workbench/workbench.tsx` | 可选菜单、命令搜索、活动栏、侧栏、对话区、底部面板和状态栏；任务只传入需要的插槽 |
| 通用页签与标题 | 同文件的 `EditorTabs`、`PanelHeading` | 受控页签与面板标题，不读取业务状态 |
| 能力清单 | `components/workbench/capability-browser.tsx` | 接收注册数据，搜索、展开版本与能力信息、标记已选用项 |
| 图文展示 | `components/workbench/document-renderer.tsx` | 安全 Markdown/GFM、图片、声明式流程图、浏览器图片压缩 |
| 通用文本编辑器 | `components/workbench/markdown-editor.tsx` | 受控 Markdown 编辑、预览、分屏、选区格式化；业务按钮与空态通过插槽传入 |
| 通用运行流程 | `components/workbench/execution-flow.tsx` | 接收节点、边、状态和选择事件；支持连接线、拖动、缩放和进度跟随；不读取 PRD API |
| 通用详情弹窗 | `components/workbench/detail-dialog.tsx` | 原生 dialog、键盘焦点管理、关闭与焦点恢复；业务内容通过 children 注入 |
| 通用原型画布 | `components/workbench/prototype-canvas.tsx` | 受限组件渲染、页面跳转和同源截图，不执行模型返回的代码 |
| PRD 状态 | `lib/use-prd-studio.tsx` | 简报、保存、草稿、导入导出、任务 SSE、版本、恢复和错误处理 |
| PRD 模块 | `components/prd-studio/` | 分组简报编辑器、澄清与修订对话、业务样式 |
| PRD 页面 | `app/prd-studio/page.tsx` | 组合通用容器与业务模块，定义 PRD 菜单、命令、工具栏和素材页 |

通用容器不依赖 `/api/prd`、PRD 字段、数据库或模型供应商。除主编辑区外，所有布局区域均可省略；没有内容时不渲染容器或切换按钮。业务内容通过 `ReactNode` 插槽传入：`toolbar`、`sidebar`、`children`、`assistant`、`bottom`、`status`、`statusRight`。容器持有布局尺寸、面板展开和命令搜索状态；折叠对话区保持组件挂载，避免丢失未完成请求和待应用建议。

命令使用 `{ id, label, run, disabled }`；菜单与命令搜索共享命令定义，调用方负责权限、并发锁和错误显示。视图使用 `{ id, label, icon }`，通过 `activeView` 与 `onView` 控制业务面板。`EditorTabs` 使用 `value` / `onChange` 控制标签。PRD 使用软件式布局：顶部文件、编辑、视图、运行、帮助菜单、左侧资源、Agent、Skill 管理、中央编辑页签、右侧 AI、底部状态栏。默认简报、原型设计、正文三个主标签；辅助标签只在选中时出现，`onClose` / `closableIds` 提供关闭入口。首次空闲时不占用运行面板；启动任务自动展开底部运行面板，可收起或展开高度。流式输出、节点详情、运行记录、历史追溯统一放在该面板，对话区不重复展示上下文标签、澄清／正文切换和运行输出。资源、Agent、Skill 分别在活动栏切换。视图菜单提供活动栏文字显示开关，偏好保存在浏览器；隐藏文字时仍保留悬停提示和可访问名称。保存归属文件菜单（Ctrl/⌘ S），生成统一由顶部“运行”菜单触发，已有正文时引导修订；文件名放在正文页签。布局沿用第一版的分组工作台，统一缩小字体与间距。窄屏可收起侧栏与 AI。

## 接入第二种工具

1. 新建路由，例如 `app/research-studio/page.tsx`，在 `AppShell` 中声明该工具使用独立工作台布局，再添加首页链接。
2. 新建该工具自己的状态 hook 和 API 边界，不复制 PRD 的字段、任务动作或存储键。
3. 根据任务定义必需组件与按需组件，导入 `Workbench`，只传入需要的插槽。保留软件式交互外壳，按任务选择左侧内容与辅助面板，不为未来需求预留空容器。
4. 复用 `EditorTabs`、`PanelHeading`、`MarkdownEditor` 与 `DocumentRenderer`；能力注册信息结构相同才复用 `CapabilityBrowser`。
5. 用真实接口控制禁用状态和进度；未实现的外部服务明确说明，不渲染会假装成功的按钮。

容器不预设“所有工具都生成 Markdown”。表格、画布、代码编辑器都可放在中间插槽。当前顺序流程图只是可复用的轻量组件；接入专业绘图服务时应由业务模块负责请求、权限、产物与任务追溯，容器保持不变。

## 澄清与生成

`POST /v1/prd/assistant` 接收可为空的简报、当前消息、最多 8 条历史消息和思考开关。服务端验证结构、字段名和合并后的字段长度；返回回答及建议，不写入文档。前端展示建议并在应用前检测字段冲突。模型连接失败、截断或返回非法结构时提示重试，不用固定回复冒充模型成功。

澄清使用一次有超时的模型调用，完成后显示回答；原型设计、正式生成、修订、评审沿用持久任务与 SSE，保留失败、停止、检查点恢复和版本追溯。DeepSeek 思考参数按下一次请求生效，运行期间开关仅改变已返回内容的显示。服务端密钥不进入浏览器。

## 媒体与保存

图片在浏览器压缩后以受限的 `data:image` URL 写入 Markdown。Python `prd/media.py` 在模型调用前将图片编码替换成稳定哈希引用，发布前恢复原始图像，并保留模型遗漏的原文图片。流程图使用 `nexus-flow` 代码块和声明式 SVG，预览禁用原始 HTML；不执行上传的 SVG 或任意脚本。文本模型并未读取图片像素。

正文及媒体总计最多 200,000 字符，超限不发布；图片原文件最多 8 MB，压缩最长边 960 像素。更大的素材库、对象存储、图像理解和生成式绘图是后续扩展。Markdown 导出保留源格式，HTML 导出可直接显示图片和流程图。

详细操作与部署边界见[写作工作区指南](../reference-apps/nexus-prd/authoring.md)。接口回归位于 `tests/integration/test_prd_studio.py`，覆盖空白简报、建议校验、历史限制、思考参数、错误脱敏和图文修订。

`Workbench.showActivityLabels` 控制活动栏文字，默认显示；隐藏仅移除视觉文字，保留 `title` 与 `aria-label`。PRD 将该偏好存储在 `nexus-workbench:activity-labels`，存储不可用时仍可临时切换。

## 可复用附件入口

`components/workbench/attachment-dropzone.tsx` 负责文件选择、多文件拖放、读取中状态和局部错误。`accept`、`disabled`、`onUpload(files)`、`onBusy` 由调用方提供，渲染函数向宿主提供 `open()`，可放入任意输入框的工具栏。组件不预设文件如何上传或保存。

PRD 通过 `lib/prd-attachments.ts` 将一个批次准备成文本来源及原型页面，全部验证通过后一次性更新工作区；由页面把读取状态并入任务与编辑锁。`PrdAssistant` 从实际简报的材料与原型派生附件列表，不另存可能过期的附件副本。对话清空不删除工作区资料；文本进入模型上下文，图像仍遵循配图与文字模型隔离规则。

PRD 不传入 `Workbench.toolbar`，运行命令统一由菜单触发，避免一行只放一个按钮。软件式外壳的保留不要求空工具栏常驻；正文自己的格式工具栏仍在编辑时使用。


## 原型与运行面板（2026-09-11）

新增 `prototype-editor.tsx` 和 `run-panel.tsx` 作为 PRD 业务组件。简报在主编辑区维护；AI 对话根据当前编辑对象处理需求澄清、原型修改或正文修订，不再重复放编辑对象标签。运行面板通过 `Workbench.bottom` 接入，`bottomFocusToken` 保证新任务或菜单操作可重新展开被隐藏的面板。

原型是之前“配图”的明确业务含义，不是另起一份无关素材。已有正文中的内嵌配图可纳入原型设计；新导入图片直接成为原型页面。AI 使用现有 `user_flow` 能力生成受限页面 schema，经 Runtime 校验后保存为待确认版本；不能输出任意 HTML、脚本、网络 URL 或自行确认设计。当前 5 种声明式组件为 text/input/button/list/card，支持按钮跳转或显示操作说明，是用于核对页面和交互的线框原型，不连接真实业务数据。

`brief.prototype` 保存页面、组件、说明、截图和确认摘要，沿用文档保存、草稿和版本历史。用户确认时，浏览器用与预览相同的 SVG 渲染器生成 JPEG 截图；导入图片沿用原图压缩结果。确认摘要绑定规范化的简报文本和来源；需求变化会失效，重新确认可与未保存需求一并提交。每个原型最多 4 页、每页最多 8 个组件、截图合计最多 140,000 字符；最终图文仍受 200,000 字符限制。图片内容不会进入文本模型，上游提供结构化页面和交互说明。生成／修订末尾由代码插入对应截图及说明，修订时替换已标记的原型章节，避免重复附图。它们随 Markdown / HTML 导出；与具体 FR 的语义对应仍需人工评审。

运行 action 新增 `prototype`，仍采用持久任务、能力路由、SSE、取消、检查点及版本机制。服务端发布 `plan`，SSE 根据任务更新时间推送，不只等待模型文本变化。运行面板展示任务实际阶段和准备环节，只有真实 running 节点呼吸高亮；失败、停止和未执行分别呈现。点击节点打开信息弹窗并固定当前节点；“概览、输入、输出、节点记录”展示真实任务目标、Agent/Skill、时间、Token、多次模型请求及阶段结果。关闭弹窗返回画布，打开“跟随进度”恢复跟随。

`GET /v1/prd/jobs/{id}/events?after=&limit=` 提供限定任务的增量事件；面板运行时轮询、终态补齐，不以拉取完整历史证据包代替进度订阅。运行记录默认中文事件、时间和耗时，技术字段折叠；历史追溯保留输入快照、任务历史、恢复和 JSON 导出。旧 `/prd` 继续使用原界面，新版在首次编写／修订前要求确认原型；旧版没有原型的文档仍可按原流程处理。

验证新增于 `tests/integration/test_prd_prototype.py`：真实编排中的原型产物、确认门槛、截图保留、修订去重、需求变更失效、事件游标隔离及非法模型输出拒绝。受控模型用于验证交互与数据契约，不代表真实模型设计质量已通过验收。


### 节点画布与详情弹窗

运行区域采用类似 Langflow 的节点画布：点阵背景、节点卡片、输入输出连接点、带方向的曲线连线，运行中的节点与入边动态高亮。`ExecutionFlow` 接收显式 `nodes` / `edges`，PRD 按实际阶段顺序构建边；画布负责展示，不从模型文字猜测依赖。拖动空白处平移，滚轮或按钮缩放，“适应画布”显示整个图；节点也可拖动，连线随位置更新。这些操作只改变当前视图，不能修改后端流程、节点状态或依赖，切换视图不持久化布局。

`DetailDialog` 是可复用原生 dialog 容器，通过 portal 显示，支持 Escape、关闭按钮和遮罩关闭、焦点约束与关闭后返回触发节点。节点弹窗中的字段由 PRD 模块映射实际 trace：缺失记录显示“尚无记录”，模型调用数按请求事件统计，Token 按已返回响应统计，耗时按阶段完成／失败事件统计。查看节点时暂停自动跟随，避免运行更新切走用户正在阅读的内容。完整运行记录与历史追溯仍在画布同区域的子标签中。尊重系统减少动画偏好。


### 可拖动面板尺寸

`Workbench` 统一管理左侧栏宽度、右侧 AI 面板宽度、底部面板高度，中间编辑区使用剩余空间。三处分隔线复用 `PanelSplitter`，支持鼠标／触摸拖动、方向键以 10 像素调整、Shift + 方向键以 40 像素调整、Home / End 到边界，以及双击或 Enter 恢复默认。隐藏面板时分隔线一同隐藏；折叠 AI 区保持内容挂载。

`usePanelLayout` 通过 ResizeObserver 获取可用空间，保留编辑区至少 320 像素宽和约 180 像素高，边栏与运行面板按边界限制尺寸。窗口缩小时只收缩实际显示尺寸，不覆盖用户首选尺寸；窗口扩大后恢复。极窄窗口可折叠侧栏或 AI，必要时横向滚动。默认左栏 215、AI 330、运行面板 370 像素。

首选尺寸保存在 `layoutStorageKey`（默认 `nexus-workbench:layout:v1`）对应的 localStorage 中，读取时校验数值范围；存储不可用时仍可调整本次页面布局。其他工具可传入独立存储键。`bottom` 可接受 ReactNode，或接收 `{ expanded, toggleExpanded }` 的渲染函数；“展开／还原”由外壳统一控制，与拖动一致。业务运行组件填满父容器，不再设置自己的固定高度。

Markdown 分屏也复用 `PanelSplitter`，编辑与预览比例保存在 `nexus-workbench:markdown-split:v1`；可用宽度不足 480 像素时改为上下排列，恢复宽度后沿用原比例。调整布局不改文档、原型或执行状态，画布通过自身 ResizeObserver 适应新区域。

顶部命令搜索只显示“搜索命令…”，不显示快捷键后缀；Ctrl/⌘ Shift P 仍可打开命令搜索。
